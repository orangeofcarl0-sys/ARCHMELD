# AOCI-CODE 纳入评估

评估日期：2026-11-24。评估对象：`aoci-spec/aoci-code`（`d28c8566`，
v0.2.0-rc4，FSL-1.1-MIT）。同时复核上游 `codegraph-ai/CodeGraph`
`590c2ca7..ae4b2e54`（0.21.2）。

## 0. 结论

1. **不把 aoci-code 作为代码或子系统并入 ARCHMELD。** 它是 Go 编写的约
   20 万行独立产品，和 ARCHMELD 的 Rust 证据账本、快照、静态调用图、
   review/brief 生命周期是两套东西；直接 fork 会同时引入许可证、双运行时、
   协议演进和治理重复四类成本。
2. **采纳它解决“模型不愿用工具”的机制，而不是它的实现。** AOCI 的关键
   不是索引算法，而是把“先读系统认知”变成会话开始的强制契约、把认知
   写成 Git 中可读的持久文本、把陈旧/缺失变成显式状态。ARCHMELD 的 M1
   已经有 `status`/`brief`，但触发条件仍是“需要调用关系时”，不是每次
   会话开始；这是依从性差距，不是图精度差距。
3. **把 AOCI 作为可选的上游认知层做只读互操作。** 当仓库里存在
   `aoci.txt`/`aoci.code.txt` 时，`archmeld_brief(recipe=change)` 应列出
   本次改动会影响哪些 AOCI Entry，`recipe=project` 应给出 Entry/Volume
   计数；ARCHMELD 不写 AOCI 文件，不复制其代码，不依赖其二进制。
4. **不把“模型作者认知图”直接做成 ARCHMELD 的默认输出。** 模型作者语义
   成本高（AOCI 自述约 1 小时/20 万行）、易漂移，而且和 ARCHMELD 的
   “候选边不得升级为已解析调用”边界容易混淆。等 A1-A3 的依从性实验
   证明收益后，再评估“证据绑定认知层”（E 方案）。
5. **上游 0.21.2 值得合并。** 四个提交是真实缺陷修复：PHP 方法调用按
   接收者类解析、LSP 模式遵守 `--max-files`/`--exclude`、引擎线程上限、
   VS Code 引擎下载加固。与本地补丁只有 `main.rs` 一处冲突，已本地合并，
   回归测试见第 2 节。

一句话：AOCI 证明的是“把认知变成会话仪式”有效，不是“再建一个图数据库”
有效；ARCHMELD 应学仪式和可读性，不应学它的体量和写入协议。

## 2. AOCI-CODE 到底是什么

### 2.1 它解决的问题

CodeGraph/ARCHMELD 回答“这个符号被谁调用、这次改动影响谁”；AOCI 回答
“这个系统由哪些对象组成、每个对象负责什么、改它必须同时考虑什么”。
前者是查找工具，后者是系统认知层。AOCI README 自己把两者定位为互补：
“index to know the system, CodeGraph to fetch the exact code while working”。

### 2.2 它怎么让模型使用它

AOCI 的依从性不靠工具描述，而靠四件事：

1. **会话开始的无条件契约。** `init --agent` 把一段受管 `AGENTS.md` 写入
   仓库，要求每个新 Agent Run 先判断是否有可用完整索引；没有就先
   `aoci_rules` 再 `aoci_overview`，读完整个索引后才开始业务任务。
2. **索引是仓库里的持久文本。** `aoci.txt`/`aoci.code.txt` 与代码一起
   提交，模型可以直接读文件，也可以走 MCP；换会话、换 Agent、换机器都
   还在。ARCHMELD 的 brief 是每次调用现算的 JSON，不持久。
3. **读完后要证明。** `aoci_overview` 分块交付，每块带 `chunk_sha256`
   和游标；完整链结束后提交 Attestation，按 Entry 序号回答 Challenge。
   未通过时只能声明“已加载/已交付”，不能声明“已理解整个系统”。
4. **维护是完成定义的一部分。** `aoci_maintain` 把 Missing/Orphan/
   Stale/Unbaselined 显式列出；改完代码不维护，下一次会话就会看到 Drift。

这四件事的共同点是：**把“用不用工具”变成“任务是否完成”的一部分**，
而不是在需要时可选地查一下。

### 2.3 它不是什么

- 不是调用图：没有 parser、没有符号级调用边、没有源码范围、没有 runtime
  trace；`R` 是指向仓库相对路径的强关系，不是经过解析的 call edge。
- 不是自动语义：规范明确禁止程序选择 tag、生成/预填/压缩 F/R/A/S；
  语义必须由模型读证据后写。机器只能做证据收集、指纹、漂移检测、格式
  校验和治理。
- 不是知识图谱/向量库：README 明确说没有 graph database、vector database
  或远程图服务；派生投影必须标 `derived=true`，不得冒充权威。
- 不是零成本：首次索引按小时计，每会话按万级 token 计；Issue #196 的
  用户就在问能否按模块拆索引，维护者拒绝，理由是跨模块依赖才是改代码
  最容易错的地方。

## 3. 为什么“模型对 CodeGraph 依从性不好”

先把已知证据摆清楚：

- 2026-11-03 的同 Agent 对比中，ARCHMELD 臂被明确告知“ARCHMELD 是主要
  证据源”，并拿到完整 HTTP 调用清单；结果两臂都是 17/17 字段、4/4 任务、
  0 次补信息。ARCHMELD 臂成本 14 次工具调用/229,400 tokens/66.7 s，
  基线 9 次/140,449 tokens/39.0 s。**这个实验测的是证据正确性，不是
  自然依从性**：它没有回答“没人告诉模型要用时，它会不会用”。
- AOCI 的 Issue #196 证明相反方向的成本：完整索引每会话约 14 万 tokens；
  维护者认为这是必要的一次性全局认知，拒绝按模块拆分。
- AOCI 的 Issue #168 证明协议复杂度会把成本转给宿主：六个
  “行为/文档不一致”需要宿主自己写适配代码，包括重发批次理由变化、
  Finding 分两次报、Maintain 不返回 Volume 路径、宿主中断被误判容量不足、
  游标错误形状不一致、中性根识别。**复杂协议不会自动提高依从性，只会
  把依从性变成宿主适配工作。**

据此，依从性差的可能原因按优先级排序：

1. **触发条件太弱。** 现在的规则是“需要调用关系时先用 ARCHMELD”，
   模型要先判断“我是否需要调用关系”；大多数局部编辑它会判断为不需要，
   于是直接 grep/read。AOCI 的规则是“每个新 Run 先建立认知”，没有判断
   空间。
2. **收益不可见。** 一次 `archmeld_query` 返回的是实体/边/证据 ID，模型
   还要再 `source` 才能看到代码；grep 一次就能看到行。除非任务明显跨文件，
   模型自然选短路径。AOCI 的 Entry 本身就是可读的一句话，读一次就
   有系统级收益。
3. **结果太大/太 JSON。** 8 个工具的 schema 和结果都是结构化 JSON；
   模型要在上下文里解析字段。AOCI 的 `aoci_overview` 是分块纯文本，
   每块 4k-24k tokens，读完即用。
4. **没有完成定义。** 不用 ARCHMELD 不会导致任务被判定未完成；AOCI 的
   `aoci_maintain`/Drift 会让“没维护”在下次会话显式出现。
5. **没有证明机制。** 模型可以声称“我看过了”；AOCI 用 Attestation 把
   声称变成可检验的 Challenge。

这不是说 AOCI 的答案全对。它的 14 万 tokens/会话、1 小时/20 万行、
rc4 协议摩擦，说明“强制全局阅读”本身也很贵。正确的结论是：
**依从性是工作流经济学问题；要让收益在模型做决定的那个时刻可见，
并且让跳过它有代价。**

## 4. 对比矩阵

| 维度 | ARCHMELD | CodeGraph（上游） | AOCI-CODE |
| --- | --- | --- | --- |
| 主产物 | 不可变快照 + SQLite 证据账本 + 静态图 | 图数据库 + 向量索引 | Git 中的 FRAS 文本认知图 |
| 语义来源 | 解析器/构建配置/SCIP；候选与已解析分离 | 解析器 + embedding | 模型作者；程序只治理 |
| 精确调用/影响 | 有；带 basis/resolution/evidence | 有；42 工具 | 无；R 是路径级关系 |
| 源码范围/历史 | 有；快照内 CAS 字节 | 有 | 无；只有 Entry 文本 |
| 新鲜度 | snapshot + working-tree review | watcher/daemon | Baseline + Missing/Orphan/Stale/Unbaselined |
| 每会话成本 | 按查询；可很小 | 按查询 | 一次完整 overview，约 14 万 tokens 量级 |
| 首次成本 | 秒级到分钟级索引 | 秒级到分钟级 | 约 1 小时/20 万行 |
| 写入 | MCP 只读；apply 走 CLI/HTTP 显式路径 | 可写图/索引 | 3 个 MCP 写工具 + CAS 治理 |
| 语言 | Rust，七语言组验收 | Rust，多语言 | Go |
| 许可证 | Apache-2.0（上游）+ 本地 | Apache-2.0 | FSL-1.1-MIT（竞争性商业限制） |
| 最适合 | 改动影响、证据审查、快照绑定 | 符号查找、语义搜索 | 跨会话系统认知、接手大仓库 |

结论：三者不是替代关系。AOCI 的 README 已经给出正确组合：AOCI 负责
“知道系统”，CodeGraph/ARCHMELD 负责“取准确代码”。ARCHMELD 的差异化
是**证据绑定**：候选边、快照、review 的 confirmed/candidate/unknown/stale
是 AOCI 没有的；AOCI 的差异化是**持久、可读、跨会话的语义层**，是
ARCHMELD 目前没有的。

## 5. 选项与判定

### A. 直接 fork/vendor aoci-code 进 ARCHMELD

- 代价：20 万行 Go、独立二进制、独立 MCP 服务、FSL 竞争性限制、rc4
  协议演进、与证据账本重复的 Baseline/CAS/ledger。
- 收益：省掉自研认知层的时间。
- 判定：**拒绝**。ARCHMELD 不需要第二个 Go 运行时；AOCI 的写协议和
  ARCHMELD 的只读 MCP 边界冲突；FSL 使“作为商业产品的一部分”需要
  法律评估；它的语义不可由 ARCHMELD 的图自动生成，无法复用我们的
  最强资产。

### B. 用 aoci-code 替换 CodeGraph/ARCHMELD 的图核心

- 代价：丢掉调用图、影响分析、源码范围、快照、SCIP、七语言验收和
  211 项回归；PHP/Java/C# 等解析能力归零。
- 判定：**拒绝**。AOCI 自己都说它不是 knowledge graph、不推断业务
  语义；它不能回答“谁调用它”。

### C. 只读互操作（AOCI 作为可选上游认知层）

- 做法：检测 `aoci.txt`/`aoci.code.txt`；解析 Volume 和 Entry；在
  `archmeld_brief(recipe=change)` 中列出受改动影响的 Entry，在
  `recipe=project` 中给 Entry/Volume 计数；`archmeld_status` 给
  `cognition_map` 状态。只读、软失败、不依赖 `aoci` 二进制。
- 收益：直接兑现“用 AOCI 知道系统、用 ARCHMELD 取准确代码”；让
  ARCHMELD 成为两者之间的桥；成本低（纯文本解析 + 一个测试 fixture）。
- 风险：AOCI 格式是 rc，需按 `aoci-index-format-v1` 做容错；不能把
  Entry 当作已解析关系。
- 判定：**接受，作为 M2.5 的可选切片**。

### D. 采纳依从性机制（不采纳 AOCI 的实现）

- 做法：
  1. 规则改成**会话开始契约**：每个新 Run 在做计划/编辑前先
     `archmeld_status` + `archmeld_brief(recipe=auto)`；编辑后
     `archmeld_review` + `brief(recipe=change)`，最终答复带 snapshot 和
     confirmed/candidate/unknown 计数。
  2. `archmeld_brief` 的 MCP 结果增加一屏 markdown（JSON 仍保留），
     让模型直接读结论，不用解析字段。
  3. 可选 `archmeld brief --write` 生成 `.archmeld/SESSION.md`，带
     snapshot/commit/working-tree/counts/unknowns 头；`archmeld_status`
     报告 `session_card` 是否与当前快照匹配；规则要求“存在且新鲜才读，
     不新鲜就重新生成”。
  4. `archmeld init --write` 安装规则 v2；默认仍不写用户仓库。
- 收益：直接针对“触发条件太弱/收益不可见/没有完成定义”；不引入新
  运行时；保持只读 MCP；可测量。
- 风险：持久 card 可能过期；规则变长会增加上下文；需要实验证明不是
  又一堆“写了没人用”的提示。
- 判定：**接受，作为 M2.5 主切片**。

### E. 证据绑定认知层（长期）

- 做法：模型作者 FRAS 风格 Entry，但每条 R 必须绑定 snapshot 中的
  entity_id/relation，或显式标 `unknown`；`archmeld map check` 验证，
  `archmeld map maintain` 按快照 digest 列出 stale；写路径走 CLI
  `--write` + 文件哈希，不进 MCP。
- 收益：同时拿到 AOCI 的“持久语义”和 ARCHMELD 的“证据绑定”，是
  真正的差异化。
- 代价：模型作者成本、语义正确性、写入治理、与 M1 brief 的边界；
  至少是一个独立里程碑，不应在 A1-A3 验证前启动。
- 判定：**暂缓，设门禁**。只有 A1-A3 实验显示依从性/成本可接受，
  才进入设计。

## 6. 推荐落地顺序

### M2.5-A：规则 v2 + 可读 brief（1 个切片）

- `docs/agent-rules/AGENTS.md`、`claude.md`：改成“会话开始/编辑后”的
  无条件契约；保留 candidate/coverage/verification 边界。
- `archmeld_brief`：MCP 返回第二个 `text` content（markdown 一屏）；
  保持 JSON 第一项不变，避免破坏现有客户端。
- `archmeld init --write`：安装规则 v2；`--check` 握手不变。
- 测试：MCP stdio 断言两个 content item、markdown 含 counts/next；
  rules 文本含 `archmeld_status`/`archmeld_brief` 且不含 `codegraph_*`。

### M2.5-B：可选会话卡（1 个切片）

- `archmeld brief --write [--out PATH]` 写 `.archmeld/SESSION.md`；
  默认路径可被 `--out` 覆盖；不自动加入 Git，不自动提交。
- 文件头：`snapshot_id`、`commit`、`workspace_state`（clean/dirty）、
  `generated_at`、`coverage`、counts；正文复用 `render_markdown`。
- `archmeld_status` 增加 `session_card: {present, path,
  snapshot_match, workspace_dirty}`；MCP `status` 原样透出。
- 测试：写入/读取/快照不匹配/工作区 dirty/路径含空格；不覆盖用户
  已有同名文件除非 `--force`。

## 7. 风险与护栏

- **不复制 AOCI 代码。** C 方案只读其公开文本格式；FSL 的竞争性限制
  不适用于“读取用户仓库里的文本”，但直接复制实现需要法律评估。
- **不把 AOCI Entry 当证据。** Entry 是模型作者语义，不是解析器事实；
  brief 中必须标 `provider=aoci`、`verification=not_run`，不得写成
  confirmed relation。
- **不自动生成语义。** 即使做 E，也由模型作者、ARCHMELD 只校验绑定，
  不做“从 AST 生成 F/R/A/S”；这既符合 AOCI 的边界，也符合 ARCHMELD
  的候选/已解析分离。
- **不默认写用户仓库。** SESSION.md 必须显式 `--write`；不自动提交；
  不覆盖已有文件除非 `--force`；文档说明它可被删除/重新生成。
- **不让 card 变成第二真相源。** card 只是快照的投影；`status` 必须
  报告 stale；最终答复必须引用 snapshot/counts，而不是 card 的生成时间。
- **不新增 MCP 写工具。** AOCI 的 `maintain/update/remove` 不进
  ARCHMELD MCP；任何写入仍走 CLI/HTTP 的显式路径。
- **Windows。** 路径含空格/非 ASCII、CRLF、长路径、ReFS；测试覆盖。
- **大仓库。** card/brief 必须有预算和截断标记；不能把 242 KB 的
  AOCI 索引整段塞进 brief。
