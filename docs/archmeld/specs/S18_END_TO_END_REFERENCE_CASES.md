# S18 · 三个端到端验收旅程

以下均为**待实现的测试情景**，不是用户现有项目诊断结论。

## Case A：Python 研究程序，一次性整理

输入是有 CLI、数值计算、绘图和全局状态的中型 Python 工程。Expedition 默认不写源码。Agent 定位输入数据路径、单位、随机种子和状态更新，导入 VizTracer，查出一个重复计算/共享状态机制，提出最小修复与不改的代价。

先建立数值和动态行为契约；在暂存区分离 I/O 和算法状态，运行原有测试与合成真值。预览 diff 与证据后批准应用。原目录在批准前字节不变；应用后验证并导出离线报告。验收核对 baseline/candidate、运行 Trace source mapping、用户未提交文件、报告无密钥。

## Case B：C++ + Python + UI，长期维护

Manager 保存职责图、采集与估计状态所有权、FFI 边界和关闭场景。加入场景：正常流、慢消费者、队列饱和、取消、设备断开（模拟设备，不默认访问真实硬件）。

若观察到共享锁导致等待，不能只看函数 duration 就判根因；检查线程/队列/锁交接。目标架构明确 buffer owner、结果快照、UI 消费契约。迁移分步保留旧入口，验证不丢消息/不覆盖缓冲区、关闭资源与数值结果。

随后用户手工修改一个接口，工作台自动标记相关证据和 Claim 过期，而不是修改批准历史。重启后状态完整，旧 Trace 仍打开旧代码。此用例验证持久 manager 的核心价值。

## Case C：JS/TS 服务，多语言协议边界

代码含 frontend、API、任务 worker 和一段 Go/Rust/C# 示例服务（各语言验证分开做，不要求全部塞一个巨型 fixture）。用协议或路由绑定建立边界候选，OTLP span/link 证实某场景的因果链。时间相邻但没有 correlation 的事件不得自动连接。

目标是隔离重试/幂等职责。冻结请求/错误/重复消息/超时契约；语义 rename 或提取模块并验证构建和场景；保证字符串配置、同名无关符号不被批量替换。所用语言的 golden fixture 与真实项目测试均通过才算其语言能力 verified。

## 跨案例共通失败情景

在 plan 与 apply 之间手工改文件；在第 N 个文件写入时杀进程；验证期间改契约；Trace 中加入路径穿越和脚本；工具缺失；采集超时；换构建宏。预期是拒绝/冲突/部分/恢复而不是绿色成功。每个情景都必须保存真实测试执行证据。
