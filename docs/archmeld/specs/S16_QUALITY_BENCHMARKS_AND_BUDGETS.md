# S16 · 质量指标、资源预算与基准

## 1. 不使用不可验证的宣传数字

上游宣称的语言数、查询速度和 token 节约不是本产品测试结果。发布前必须在声明硬件、工具链和数据集上测量，记录热/冷状态、缓存、数据规模与重复方法。

## 2. 正确性优先级

金标测试中，所有宣称 resolved 的关系精确率必须为 100%；它是有限 fixture 上的发布门槛，不是对任意项目的证明。同时报告召回率、未解析比例和覆盖分母，不能通过全部返回 unresolved 获得“完美精度”。每语言所列必需 fixture 关系召回率亦须 100%，真实项目则展示人工抽样审查和局限。

代码—图—Trace 链接必须指向正确 snapshot/range。任何误指当前文件、版本混合、越权写入或错误恢复都是 release blocker，不用平均分稀释。

## 3. 基准数据级别

T0：几十文件的确定性金标；T1：各语言真实中小工程；T2：多模块混合工程与十万级符号压力数据；T3：百万事件 Trace 和增量变更风暴。fixtures 原始来源和许可证明确，不能包含私密用户项目。

T2/T3 可用合成压力数据测资源，但业务正确性必须另外在真实工程上验证。对七语言各选一个固定公开样本与构建命令，纳入 fixtures.lock；不要在测试时随机 clone main。

## 4. 起始 SLO（待实测验收，不是已达成）

在声明的参考机、已索引 T1 上：本地实体查询 p95 ≤ 300 ms；选中节点到源码高亮 p95 ≤ 500 ms；取消任务后 3 s 内停止新增受管理子进程并反馈状态；工作区轻量修改 1 s 内标记相关结果 stale。索引完成时间、RAM、CPU、磁盘与 Trace 开销先测量后设工程预算，不预先编造能处理任意仓库的阈值。

预算超限必须部分结果/错误+诊断，不悄悄跳文件。用户可提高限制，但修改配置要记录到分析 run。UI 渲染图分页和惰性展开，不能一次渲染全仓几十万节点。

## 5. 理解质量

建立固定问题集：入口与生命周期、状态所有权、跨边界交互、异常/取消路径、运行瓶颈、变更影响。评价答案引用完整性、证据冲突处理、是否区分推断/观察、是否识别缺口。自动评分只能辅助；发布样本需人工检查，模型自评分不能作为唯一标准。

## 6. 可维护性

监控 fork patch 数量/规模、适配器耦合、契约版本漂移、schema 生成差异。重用上游不能发展为大量复制粘贴私有实现。错误归因要定位到核心、adapter、upstream 或目标工程，不统一甩给模型。
